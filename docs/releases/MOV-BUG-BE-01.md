Подтверждённая локальная причина блокировки из пакета Тимлида — сохранённая
active/pendingEnd запись не получает ack при 404 sync, поэтому abort не отправлен.
Это защита данных, а не доказательство неисправности серверного abort.
Несовместимость опубликованного Worker остаётся гипотезой: для её подтверждения
нужны доступ к health, существующая сессия проверочного профиля и read-only доступ
Cloudflare к выбранной D1. Секреты в чат не передавать; подключать через защищённую среду.
Отсутствие 0005 и отсутствие маршрута — разные причины: отсутствие таблиц обычно
даёт 500, а не доказывает 404. Один health/401 тоже не доказывает поддержку программ.

## Проверенный код и изменения

cloudflare.js передаёт /api/v2/* в handleApi после проверки Bearer и Origin.
api.js нормализует /api/v2/ в /api/ и передаёт workout GET/POST в workouts.js.
sync([]) создаёт выполнение/шаги без событий и XP. Abort допускает нулевой и
частичный итог; условный UPDATE переводит active в aborted. hasActiveWorkout и
SQL start guards учитывают только active. Повтор sync с прежними UUID и повтор
abort не удваивают работу и не возвращают терминальный статус в active/completed.
Контракт и guards deploy-backend.mjs сохранены; искусственный обход не добавлен.

## Checker: запуск и смысл результата

Node 24 использует существующие parseWorkoutCatalog/parseActivity/parseWorkoutPage.
Ввод только из окружения: WORKOUT_API_BASE (по умолчанию канонический /api),
WORKOUT_API_SECRET (существующие 64 lowercase hex проверочного профиля).
Credential передаётся только защищённым трём GET, не health. HTTPS обязателен;
userinfo/query/hash в base запрещены, redirect:error не допускает пересылку Bearer.
Аргументы CLI не принимаются. Исключения/тела/произвольные серверные error.code
не выводятся: используется фиксированный список безопасных кодов.

После подключения credential защищённым механизмом (без вставки в shell-команду):

```sh
node --use-env-proxy scripts/check-workout-api.mjs
```

Выход: version из валидного health, authChecked, фиксированные route/status/code,
json/valid и ready. Exit 0 — все четыре GET прошли; 1 — неготовность/NOT_RUN;
2 — неверная конфигурация. 404 NOT_FOUND/API_NOT_FOUND, 401 DEVICE_AUTH_REQUIRED,
409 PROFILE_REQUIRED, неправильный JSON/schema/MIME и NETWORK_OR_REDIRECT
различаются. Без credential выполняется только health; три проверки явно NOT_RUN.
Checker не делает POST, регистрации, профиля, начислений или отзыва сессий.
Обычные серверные побочные эффекты GET (например, штатное истечение старой минуты)
остаются поведением существующего API; checker не вводит отдельной записи в БД.
Готовность GET не доказывает POST или точную remote-миграцию.

Фактический безопасный результат запуска в этой среде:

```json
{"version":null,"authChecked":false,"health":"NETWORK_OR_REDIRECT","workoutGETs":"AUTH_NOT_CHECKED","ready":false}
```

## Восстановление существующей записи / сведения Frontend

После подтверждения совместимого API выполнить явный retry в прежнем API/profile
scope: передать прежний workout UUID и все прежние event UUID → дождаться ack →
отправить сохранённый pendingEnd abort с прежними endedAt/activeMs → получить
aborted → разрешить новый запуск без reload. Для synced=false/events=[] тоже
нужны sync([]) и подтверждённый abort: отсутствие локальных событий не доказывает,
что сервер ранее не принял выполнение. Потерянный ответ повторяется безопасно.

Active без pendingEnd можно явно продолжить только в пределах 24 часов либо
прекратить; после 24 часов продолжение запрещено, итог доставляется в прежнем
семидневном окне. При превышении окна не сообщать ложный успех и не удалять данные:
нужна отдельная ограниченная задача восстановления. Backend не расширяет окно.

Не очищать IndexedDB/профиль, не менять API-base, не выходить ради обхода,
не удалять приложение и не создавать вторую программу поверх неподтверждённой.
NETWORK/401/409/404 не стирают pendingEnd. WORKOUT_NOT_FOUND относится к конкретной
записи, NOT_FOUND к маршруту — Frontend должен различать их. Требуемая FE-проверка
совместимости до нового старта и явный retry остаются в отдельном пакете Frontend.
Опубликованный API и телефон этим PR не восстановлены; удалённое исправление
зависит от подтверждения live-состояния и отдельной команды на совместимый выпуск.

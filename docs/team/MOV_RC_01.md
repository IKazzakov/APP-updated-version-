Дата постановки: 27 октября 2026 года. Ответственный за контракт и интеграцию: Тимлид.
Статус: пакеты подготовлены для передачи двум разработчикам; результаты ещё не получены.

## Цель и связь с планом

Следующая контрольная точка [ROADMAP](../ROADMAP.md) — совместимые APK и API для
приёмки четырёх готовых программ на телефоне (этапы 2 и 10). Сдать подписанный
Android-артефакт, доработанные проверки публикации новых маршрутов и исполнимый
порядок выпуска/восстановления. Это подготовка выпуска, а не независимая проверка PR.

В текущем scripts/deploy-backend.mjs smokeBackend проверяет health, state,
v2/dashboard и гостевую авторизацию, но не проверяет маршруты программ/XP.
Эту конкретную недостающую часть выпуска закрывает Backend. Frontend закрывает
ещё не выполненную подготовку нового подписанного APK и протокола приёмки.

## MOV-RC-BE-01 — Backend: подготовить выпуск совместимого Worker

**Владелец:** Backend + БД. **База:** c413116, ветка/PR по общим правилам выше.

### Конечное поведение

После будущей разрешённой публикации проверка выпуска должна обнаруживать отсутствие
новых маршрутов, HTML вместо JSON и неправильную авторизацию. Подготовить Worker
dry-run и порядок миграции/восстановления, не применяя изменения удалённо.

### Границы файлов

- scripts/deploy-backend.mjs — только дополнение smokeBackend и открытого отчёта checks.
- tests/backend-deploy.test.js — необходимые проверки нового поведения smokeBackend.
- docs/releases/MOV-RC-01-backend.md — команды, зависимости, условия остановки,
  порядок восстановления и фактические результаты подготовки.
- work/backend/** — локальные/CI-артефакты, не коммитить.

Server API, drizzle/0000..0005, wrangler.backend.json, workflows, UI и номера версий
в этом пакете не редактировать. Существенную найденную необходимость изменения
передать Тимлиду с обоснованием; не расширять область молча.

### Входы, выходы и ошибки smokeBackend

Входы прежние: origin и внедряемый request. VERSION брать из src/config.js,
не фиксировать 2.5.4 или 2.6.0 внутри проверок. Существующие проверки сохраняются.

Добавить для каждого GET /api/v2/workouts/catalog, /api/v2/activity,
/api/v2/workouts/history?limit=1:

1. Без Bearer требуется JSON HTTP 401 с error.code=DEVICE_AUTH_REQUIRED.
2. С созданной штатным smoke гостевой сессией без профиля требуется JSON HTTP 409
   с error.code=PROFILE_REQUIRED, private/no-store.
3. HTML, неожиданные 2xx, 404, 5xx, неправильный код ошибки или transport failure
   отклоняют проверку. Ни fallback на v1, ни пропуск нового маршрута не разрешены.
4. В finally отозвать созданную сессию, в том числе после ошибки нового маршрута.

Выход сохраняет прежние flags и добавляет checks.workoutRouteGuards=true только
после выполнения всех новых проверок. Это подтверждение маршрутизации и границ
доступа; оно **не** доказывает работу с профилем/0005 или физическую точность.
Не создавать пробные профили/тренировки и не начислять XP в опубликованной базе.
Секрет сессии не выводить в журнал или отчёт. Повторный smoke создаёт и отзывает
собственную сессию, не меняя данные существующих пользователей.

### Подготовка миграции и выпуска

В отчёте указать исходный commit, SHA-256 неизменённой 0005, комплект Worker
из work/backend/dry-run, зависимости от итогового APK и команды штатного процесса.
Описать будущий порядок: резервная точка D1/проверка выбранной существующей БД →
применение 0005 штатным deploy → совместимый Worker/статика → проверки API и APK →
полный сценарий на телефоне. Учитывать активные старые клиенты: активация XP
начинается persisted-временем миграции, а не первым запуском нового APK.

Разделить неуспех до миграции, после миграции до Worker и после начала новых
выполнений. Не предлагать DROP/очистку таблиц, очередей или профилей.
Старый Worker не может финализировать программы: после появления новых журналов
нужен совместимый Worker для доставки/восстановления; откат не должен терять их.
Backup/bookmark удалённой D1 пока обозначить как действие будущего разрешённого
выпуска; не выдавать локальную подготовку за выполненную remote-операцию.

### Критерии и проверки

- Локальный smoke через настоящий Worker/SQLite проходит новые guards без профиля.
- Отсутствующий новый маршрут, неверный JSON/status/code и ошибка сети дают отказ;
  созданная сессия отзывается также при неуспехе. В БД нет новых профилей/XP/тренировок.
- Выполнены целевые tests/backend-deploy.test.js, build и backend:validate dry-run.
  Новый тест должен доказывать отказ ошибочного выпуска, а не повторять код функции.
- Подготовлены комплект и отчёт с конкретными командами и ограничениями.

**Возврат Тимлиду:** PR/SHA, diff файлов, команды и результаты, Worker-артефакт/его
место хранения, SHA-256 миграции, отчёт о выпуске, ограничения. Remote/deploy не выполнены.

## MOV-RC-FE-01 — Frontend: подписанный APK и протокол приёмки

**Владелец:** Frontend. **База:** c413116, ветка/PR по общим правилам выше.

### Конечное поведение

Доступен подписанный кандидат 2.6.0 / 20600 для установки поверх 2.5.4 / 20504
с прежней Android/API-идентичностью, а также конкретный протокол приёмки четырёх
программ. Сборка не означает успешную физическую приёмку или опубликованный API.

### Границы файлов

- package.json и только два корневых поля version package-lock.json — версия 2.6.0,
  зависимости и lock-разрешения не обновлять.
- src/config.js — только VERSION, остальные настройки не менять.
- docs/releases/MOV-RC-01-android.md — сборка, ссылки на артефакты, подпись,
  исходный SHA и протокол устройства с фактическими/NOT_RUN результатами.
- work/artifacts/** и штатные генерируемые Android/build-файлы — артефакты,
  не добавлять их массово в PR. Версия Android вычисляется существующим Gradle.

Сборочные скрипты, workflows, Capacitor appId/API, старые public/app-debug.apk*
и незашифрованные ключи не коммитить/не менять этим PR. При локальной сборке скрипт
перезаписывает public APK и создаёт Android-ресурсы; выполнять её в отдельной
сборочной копии либо исключить эти выходы из итогового diff, сохранив чужие изменения.
Клиентскую функциональность, алгоритмы и сервер не менять. Блокирующий дефект
передать Тимлиду для отдельной ограниченной задачи, не подменять его заглушкой.

### Входы, выходы, совместимость

Вход: source SHA с согласованной реализацией, JDK 21, SDK/Build Tools 36,
действующий ключ через существующий локальный путь либо Actions secret.
Читать docs/ANDROID_SIGNING.md, docs/ANDROID_TESTING.md, android/app/build.gradle,
scripts/build-apk.mjs, build-staging-apk.mjs, sync-android.mjs и два сборочных workflow.

Использовать штатный npm run build:apk:staging либо Movement — checks and APK
на своей ветке с build_apk=true. При отсутствии локального ключа предпочесть
существующий Actions secret; не запрашивать секреты в чате и не создавать новый ключ.

Выход: app-debug.apk, app-debug.apk.json, app-debug.apk.sha256,
android-manifest.txt из штатного work/artifacts или movement-android-<SHA>.
В отчёте указать source SHA, версию/versionCode, размер, SHA-256, package и открытый
отпечаток сертификата, URL workflow/artifact и срок доступности артефакта, если известен.
Доступность artifact не называть публичным выпуском или постоянной download-ссылкой.
Повторная сборка не обязана иметь тот же hash; каждый результат привязан к своему SHA
и своему SHA-256. Не устанавливать APK другого пакета и не удалять приложение ради обновления.

### Критерии и проверки

- package.json, корневые версии lockfile, VERSION и versionName APK совпадают;
  versionCode=20600 > 20504. Работают штатные проверки подписи/manifest/состава APK.
- В APK присутствуют локальные Full/WASM, нет вложенного старого APK/закрытого ключа.
  API-base, package и сертификат соответствуют общему контракту.
- typecheck, format:check, lint и build проходят; Actions выполняет свой штатный набор.
  Свежие результаты связаны с фактическим SHA, прежние числа тестов не копируются как новые.
- Артефакт собран и доступен Тимлиду. Если сборка заблокирована средой/ключом/Actions,
  вернуть точную причину и выполненное; не объявлять сборку успешной по одной конфигурации.

### Протокол телефона

Подготовить проверяемую таблицу: сценарий, ожидаемый результат, фактический результат,
device/Android/source SHA, условия камеры/освещения/расстояния, PASS/FAIL/NOT_RUN.
Включить:

1. Установку поверх существующего приложения без удаления; прежний профиль,
   история, credentials и неподтверждённые UUID сохраняются после перезапуска.
2. Четыре программы: 5 squat → 5 XP; 5 pushup → 5 XP; накопленные 15 секунд plank
   → 3 XP; pushup5 → squat5 → plank15s → 13 XP (до дневного предела).
3. Ручную контрольную выборку полных/неполных движений и корректной/потерянной позы;
   записать реальные false-positive/false-negative, условия поддерживаемого выполнения.
4. Планку через паузу/потерю позы/reload; подготовка, фон и закрытая страница
   не создают время, продолжение только явное. Нет skip/manual.
5. Потерю сети/ответа, ожидание последнего ack до finish/abort, повтор без дублей,
   частичный итог, изоляцию нового профиля и явное продолжение до 24 часов.
6. Крупные показатели с 2–3 метров, звук, ориентацию телефона, FPS, задержку
   и нагрев при продолжительном занятии. Записать измерения; не выдумывать точность в процентах.
7. Старую минуту/дуэль: прежние сроки/попытки, aborted не создаёт минутный рекорд.

Для полного цикла нужен совместимый опубликованный API; старый Worker не поддерживает
новые маршруты. Без отдельной команды на выпуск это ограничение остаётся явным.
Если физическое устройство недоступно, отдать готовый APK и протокол с NOT_RUN:
не имитировать результаты и не задерживать передачу готового сборочного артефакта.
Это не разрешение автоматически устанавливать APK или менять данные пользователя.

## Зависимости и интеграция

1. Оба исполнителя могут начать от c413116 параллельно: файлы не пересекаются.
   Backend не правит версию, Frontend не правит deploy; общие wire-файлы у Тимлида.
2. Тимлид принимает результаты в изолированную общую ветку, обновляет ROADMAP
   и фиксирует единый итоговый SHA. Merge main остаётся отдельным действием владельца.
3. Артефакт ранней FE-ветки предварительный. Перед фактическим выпуском APK,
   Worker, миграции и проверки должны относиться к одному итоговому commit;
   Android-артефакт после интеграции пересобирается штатным workflow.
4. Подготовленный пакет выпуска предъявляется владельцу. После прямой команды
   выполняется согласованный выпуск совместимого API/статики/APK и приёмка полного
   пользовательского цикла на устройстве. До этого статусы «опубликовано» и
   «физически проверено» не выставляются.
5. Личный конструктор, лиги, сообщество и продуктовое решение контрольного примера
   №9 не входят в MOV-RC-01. Возврат к ним — по следующим этапам ROADMAP.

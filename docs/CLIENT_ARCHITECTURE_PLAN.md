## Цель и границы

Сделать добавление экранов и сценариев локальным изменением: новый раздел получает собственные представление, обработчики и стили, подключается в одном месте и использует общие сервисы через явные интерфейсы.

Работа ведётся поверх тестовой 2.5.3. main, рабочий Worker movement-test-api, рабочая D1 и основной APK остаются без изменений. Для проверки будущей реализации используется отдельное приложение «Движение Тест» с пакетом com.movement.squat.staging и тестовым сервером movement-test-api-staging.

Это переработка устройства клиента с сохранением текущего поведения и дизайна. Изменения серверных маршрутов, базы, правил начислений, модели авторизации, алгоритма приседаний и добавление новых упражнений не входят в план. Номер версии на этапе планирования не повышается.

Основа — модульное приложение на существующих ES modules, Vite и Capacitor. TypeScript вводится постепенно. React, новый глобальный менеджер состояния и библиотека маршрутизации для текущих четырёх вкладок не требуются. Возможный переход на React оценивается отдельно, когда появятся конкретные требования к более сложному интерфейсу.

## Предлагаемые границы модулей

| Область | Ответственность |
| --- | --- |
| app | Запуск, создание общих сервисов, оболочка, регистрация экранов, навигация и жизненный цикл приложения |
| features/profile | Существующая панель профиля, гостевой вход, выход, имя, часовой пояс, согласие на рейтинг |
| features/today | Дневное задание, текущая неделя, её баллы и календарь |
| features/progress | Последний результат, рекорд, график, история раундов и недельных итогов |
| features/competitions | Дуэли, приглашения, рейтинги, выбор недели и периода |
| features/training | Экран тренировки, режимы, подготовка, запуск и завершение раунда, отображение результата |
| services | Транспорт, согласование версий API, загрузка данных, очередь сохранения, сессия устройства и адаптеры платформы |
| shared | Форматирование дат и чисел, безопасная работа с DOM, общие элементы и стили |
| shared/contracts | Общие описания запросов, ответов и ошибок API, проверка внешних данных |
| diagnostics | Существующие панель, технические показатели и безопасный журнал активности, подключаемые один раз в оболочке |

Физические перемещения существующих файлов выполняются по мере выделения владельца. Таблица задаёт границы, а не требует сразу переименовать весь src. Внутри небольшой функции достаточно представления и контроллера; отдельный файл создаётся для самостоятельной ответственности.

Экран «Сегодня» нужен как самостоятельный модуль, хотя в первоначальной рекомендации перечислялись тренировка, профиль, прогресс и соревнования. Профиль пока остаётся панелью, как сейчас.

Правила связей:

1. Сервисы и общие функции не импортируют main.js или код экранов.
2. Каждый экран работает со своим корневым DOM-элементом и обновляет только его. Общая оболочка и диагностика имеют собственные корни.
3. Между экранами передаются команды через координатор: например, «подготовить соревновательную попытку» или «открыть профиль». Экран соревнований не меняет DOM тренировки.
4. Общее подтверждённое состояние обновляется в одном месте. Локальные значения формы, выбранный месяц и открытые вкладки принадлежат своему модулю.
5. Камера, движок и очередь не помещаются в сериализуемое состояние. Очередь продолжает сохранять события независимо от видимого экрана.

## Этап 4. Последовательно выделить профиль, «Сегодня», прогресс и соревнования

Каждый модуль переносится отдельным проверяемым изменением.

1. Профиль: вход и выход, форма, согласие на рейтинги и открытие/закрытие панели. Сохранить запрет выхода с неподтверждёнными повторениями и возможность локально проверить камеру без профиля.
2. «Сегодня»: дневное задание, календарь и текущая неделя. Запросы смены месяца не должны смешивать результаты и отменять уже подтверждённые счётчики.
3. Прогресс: рекорд, график, история раундов, недельные итоги и кнопки загрузки следующих страниц.
4. Соревнования: создание/принятие/отмена приглашения, список дуэлей и рейтинги. Запуск попытки передаётся контроллеру тренировки через координатор.

WeeklyUI разделяется по этим владельцам: текущая неделя — «Сегодня», история итогов — «Прогресс», рейтинги — «Соревнования». Общие вычисления представления недели и форматирование выносятся в функции без DOM. Правила начислений остаются на сервере.

Шаблоны хранятся рядом с модулем в читаемых HTML-фрагментах; существующий Vite позволяет импортировать их как текст. Статическую разметку подключать один раз, динамические списки обновлять внутри своего корня. Сохранять экранирование пользовательского текста, метки доступности и фокус. Видео и формы не пересоздаются при каждом обновлении состояния.

CSS делится на общие переменные, базовые элементы, оболочку и стили функций. Экранные селекторы ограничиваются классом корня модуля; общие кнопки и карточки остаются в shared. Порядок каскада переносится с визуальной проверкой. Отступ под диагностику и safe area задаёт оболочка.

Результат: изменение прогресса не требует менять обработчики соревнований, а недельные блоки не обновляют чужие экраны.

## Критерии готовности

- main.js содержит запуск и связывание модулей; обработчики функций и их разметка находятся у владельцев.
- Новый экран добавляется собственным модулем и записью в реестре, без редактирования представлений остальных экранов.
- Нет прямого изменения DOM чужого экрана или обхода общего способа обновления серверного состояния.
- Частичный ответ, старая ревизия, ответ прежнего профиля и сбой страницы истории не стирают подтверждённые данные.
- Камера и таймеры не дублируются; повторная навигация не умножает обработчики и запросы.
- Очередь, привязка к профилю/серверу, незавершённые записи и гостевая сессия переживают обновление тестового APK.
- Диагностика доступна внизу всех экранов; управление сервером находится внутри; журнал продолжает исключать личные данные, токены, приглашения и кадры.
- Проверка типов, сборка и согласованные автоматические проверки проходят; результат реальной проверки камеры указан отдельно.
- Серверные правила, API v1/v2, рабочая база, main и основной APK не изменены этой работой.

## Порядок выполнения и контроль

План согласован. Этапы выполняются отдельными коммитами в тестовой разработке. Форматирование, контракты, состояние и перенос каждого экрана разделяются для проверки и возврата. Для отката сохраняется исходный коммит; сброс базы или очереди не нужен.

Публикация документа плана выполняется с [skip ci]: сейчас обычный push в codex/server-optimization запускает сборку APK и развёртывание staging. Планирование не должно переиздавать даже тестовый выпуск. После согласования реализации используем тестовую сборку и staging; слияние в main и публикация рабочего сервера требуют отдельного решения пользователя.

# Работа с приложением «Движение»

Общайся с владельцем на русском. Основной репозиторий —
`rojoscarlos-cpu/APP-updated-version-`, основная ветка — `main`.

## Контекст перед каждой новой задачей

Не требуй ручного копирования API-контракта в чат, если доступен репозиторий.
Перед проектированием или изменением клиента/сервера самостоятельно прочитай:

1. `docs/DEVELOPMENT.md` — работа с ветками, проверки и CI.
2. `docs/SINGLE_SERVER.md` — единственный сервер и сохранение данных.
3. `docs/API.md` — текущий общий API-контракт для всех ролей.
4. `src/shared/contracts/api.ts` и `src/shared/contracts/validate.ts` —
   клиентские типы и проверка внешнего JSON.

Определи текущую версию по `package.json` и `src/config.js`. Для frontend
прочитай `docs/CLIENT_ARCHITECTURE.md`; для backend/БД — маршрутизаторы
`server/cloudflare.js`, `server/api.js`, чтения `server/reads.js` и
`drizzle/*.sql`. В последующих задачах перечитывай изменившиеся источники;
копия контракта из старого сообщения не заменяет актуальные файлы.

В локальной рабочей копии учитывай её ветку, SHA и незакоммиченные изменения.
При чтении через GitHub явно выбирай актуальную `main`, если задача не
называет другую ветку. Не выполняй pull/reset поверх чужой работы ради
загрузки контекста. Если репозиторий недоступен, сообщи об отсутствии доступа;
не утверждай, что контракт загружен. Обычный чат с GitHub читает этот файл
только по инструкции стартового промпта; автоматическое обнаружение
`AGENTS.md` относится к агенту, работающему с репозиторием.

## Контракты и распределение ответственности

- Тимлид определяет границы задач, API-контракты и критерии приёмки.
- Backend владеет серверной реализацией и SQL, Frontend — клиентом и UI.
- Для общих типов и runtime-валидаторов назначается один исполнитель.
- При изменении API обновляй `docs/API.md`, типы, валидаторы и затронутые
  проверки согласованно в том же PR. Документ описывает существующее
  поведение; предложения помечаются отдельно. Проверяй соответствие
  реализации, а не только наличие изменений в документации.
- `drizzle/` содержит SQL-first миграции; runtime ORM в проекте нет.
  Применённые миграции не редактируются, следующие добавляются новым файлом.

## Сохраняемые инварианты

- Единственный API: `https://movement-test-api-staging.rojoscarlos93.workers.dev/api`.
  Суффикс `staging` технический; отдельной цели production/staging нет.
- Android-пакет `com.movement.squat.staging.ui`, прежний signing key и область
  хранения device-secret/очередей сохраняются ради профилей и обновлений.
- До явного гостевого входа `401 DEVICE_AUTH_REQUIRED` ожидаем.
- Повторение сначала сохраняется локально с устойчивым UUID, затем
  отправляется. `finish/abort` ждут подтверждения очереди.
- В дуэли выбирается лучшая из трёх попыток. Подтверждённый положительный
  счёт раннего abort учитывается, но раунд остаётся aborted. Минутные
  рекорды и спортивный рейтинг требуют completed за полные 60000 мс.
- Не меняй модель, WASM, пороги распознавания или начисления без задачи,
  прямо затрагивающей их. Сервер не получает кадры, звук и координаты.

## Изменения и проверка

Новая разработка выполняется в отдельной временной ветке и передаётся через
PR. Слияние в main, remote-миграции и публикация — по прямой команде владельца
соответствующей задачи. Исходный репозиторий `Test` не изменять. Секреты и
незашифрованные закрытые ключи не выводить и не добавлять в git.

Выполняй разрешённую работу самостоятельно. Подбирай проверки по изменению:
`typecheck`, `format:check`, `lint`, `npm test`, `build`,
`backend:validate` (dry-run), затронутые браузерные сценарии.
Указывай фактически выполненные проверки; камера и производительность
реального телефона подтверждаются на устройстве.

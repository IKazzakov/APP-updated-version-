Чаты не имеют общей памяти или общей гарантированной файловой системы.
Общая точка доступа — приватный GitHub: исходники, решения и отчёты в git,
сборочные файлы в Actions artifacts. Локальный путь /workspace/... не является
ссылкой передачи. Подключение GitHub требуется в каждом чате отдельно.

## Как начать работу в любом чате

1. Убедиться, что GitHub доступен инструментами этого чата и подключённый аккаунт
   имеет доступ к репозиторию. Проверить чтением актуальных main/AGENTS.md,
   docs/TEAM_CONTEXT.md и документа своей роли. Видимости URL недостаточно.
2. Прочитать [ROADMAP](../ROADMAP.md), этот реестр и полный пакет своей задачи.
   Сверить актуальные main/PR/head SHA. Для неслитой реализации читать указанный
   commit/ветку, не считать её частью main.
3. Проверить текстовый отчёт и исходники по ссылкам ниже. Если требуется бинарный
   файл, отдельно проверить доступ к конкретному Actions run/artifact и загрузку.
   Чтение кода не доказывает возможность скачать artifact.
4. Если у инструмента нет загрузки приватных ZIP, явно указать это ограничение.
   Продолжить по исходникам/текстовым данным; пересобрать из указанного commit,
   если задача допускает новую сборку. Новую сборку не выдавать за тот же бинарный файл.
   Не просить токен или закрытый ключ в чате.

После слияния правил читать актуальную main. Пока PR с ними открыт, общий вход —
ссылка на этот файл в ветке/commit PR; она передаётся всем участвующим чатам.
Наличие инструкции в репозитории само не подключает GitHub к новому чату.

## Где что хранить

| Данные | Общее место | Что передавать |
| --- | --- | --- |
| Исходники, SQL, API, wire-типы/валидаторы | Репозиторий, временная ветка и PR | PR, source SHA, base SHA, точные пути |
| План и актуальные задачи | ROADMAP и docs/team | Ссылка на полный пакет и статус |
| Решения и результаты проверок | docs/releases или docs/reviews | Текстовый отчёт с SHA, командами, результатами и ограничениями |
| Worker, APK, подробные сборочные логи | Приватные GitHub Actions artifacts | Run URL/ID, artifact URL/ID/name, срок хранения, manifest и SHA-256 |
| Ключи подписи и credentials | Существующие Actions secrets/защищённое локальное хранение | Только имя привязки и открытый отпечаток, не значения |

Важные для продолжения работы метаданные и выводы сохраняются текстом в git:
каждый чат должен иметь возможность прочитать их без скачивания большого архива.
Загрузка CI-артефакта для команды не является публикацией приложения на сервере.

## Обязательная передача результата

Исполнитель коммитит отчёт в своей ветке/PR и сообщает:

```text
ID задачи:
Репозиторий, PR и ветка:
Базовый SHA:
Source SHA и tree SHA фактически собранных исходников:
Ссылка на текстовый отчёт:
Артефакт: run URL/ID, artifact URL/ID/name, expires_at (если выдан GitHub):
Файлы: имя, размер, SHA-256; manifest и SHA256SUMS:
Команды сборки и фактические проверки:
Ограничения/NOT_RUN и следующий получатель:
```

Если сборка выполнена на merge commit PR, source SHA — реальный git rev-parse HEAD
из checkout; SHA ветки PR при необходимости записывается отдельно. Коммит отчёта
может быть позже сборки: его SHA не заменяет source SHA артефакта.

Тимлид обновляет общий реестр после проверки. Исполнители меняют свои отчёты,
а не параллельно переписывают общие статусы. Получатель подтверждает только то,
что реально прочитал/скачал/проверил; «код проверен» и «бинарный файл получен»
фиксируются раздельно. Отсутствие необязательной промежуточной сборки не должно
блокировать независимую работу Frontend.

## Срок хранения и воспроизводимость

Actions artifacts имеют ограниченный срок хранения: ссылка не обещает вечного доступа.
Срок смотреть в фактических метаданных GitHub; просроченный artifact помечать в реестре.
Исходники, lockfile, команды и текстовый отчёт остаются в git. При пересборке записать
новые run/artifact ID и контрольные суммы; не гарантировать побайтовое совпадение APK.
Финальный Worker/статика/APK выпуска собираются из единого итогового SHA.

## MOV-HANDOFF-BE-01 — Backend: общий Worker artifact

**Цель:** последующие Worker bundles доступны получателю через приватный GitHub,
а не только в файловой системе автора. **База:** e4f552f10921a2816200b8eb9c035a24734d9328
из PR №8; main на дату постановки cf50e274, исходная версия 2.5.4.
Перед началом сверить актуальную main, PR №8 и их diff; сохранить чужую работу.
Временная ветка от этой реализации, PR в codex/mov-rc-be-01; интеграция у Тимлида.

**Владелец:** Backend. **Границы:** .github/workflows/checks.yml и собственный
docs/releases/MOV-HANDOFF-BE-01.md. Общие типы/валидаторы и этот реестр — у Тимлида.
Контракты API/SQL/auth/идемпотентность/пагинация/ревизии не меняются.

**Вход:** уже существующий успешный build и backend:validate dry-run в текущем CI.
После dry-run сформировать manifest.json и SHA256SUMS для явного списка файлов
work/backend/dry-run/{cloudflare.js,cloudflare.js.map,README.md} и загрузить его
с этими файлами через actions/upload-artifact@v4. Имя — movement-backend-<source-SHA>.
Сохранять фактические source/tree SHA checkout, версию, команды, run URL,
имена/размеры/SHA-256 файлов; SHA256SUMS покрывает manifest и Worker-файлы,
не самого себя. Отдельно указать, что bundle подготовлен до завершения всех
последующих CI-проверок; наличие artifact не означает успешный полный CI.

**Выход:** artifact ID/URL/name, фактический срок хранения, текстовый отчёт в git
с полями шаблона выше и ссылкой на конкретный run. Не загружать целиком work/,
сгенерированные конфигурации с credentials, keystore или пользовательские данные.
Старый локальный e4f552f-архив не объявлять перенесённым автоматически: пересборка
на новом commit — новый artifact с собственными source SHA и контрольными суммами.

**Ошибки и приёмка:** при неуспешном dry-run не создавать успешный bundle;
отсутствие обязательного файла должно давать ошибку, а не пустой artifact.
Успешный CI-запуск создаёт artifact, доступный аккаунту с правами репозитория;
его можно получить по run/artifact ID и проверить SHA256SUMS. Передать доказательство
загрузки и проверки, а не один локальный путь. Если текущий инструмент не умеет
скачивать ZIP, сообщить ограничение и передать manifest/суммы текстом в отчёте.

**Зависимости и порядок:** изменение CI независимо от Frontend; его API/версию
не менять. Подготовка APK MOV-RC-FE-01 не ждёт этого пакета. После интеграции
финальные артефакты пересобираются из одного SHA. Main, remote-миграции,
deploy.yml и npm run backend:deploy в рамках этой задачи не выполнять.

**Проверки:** корректность YAML/diff, реальный запуск CI с dry-run, наличие нужных
файлов и manifest, проверка SHA-256 и доступности созданного artifact. В отчёте
разделить выполненное и NOT_RUN. Отдельные новые тесты продукта не требуются.

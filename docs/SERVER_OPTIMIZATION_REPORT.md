# Оптимизация сервера и диагностика — 2.5.3

Рабочая ветка: codex/server-optimization. Основа: main 2.5.2 (8fe343b).

## Что изменено

- /api/v2: компактное подтверждение повторений и ограниченная панель. Старый /api обслуживает APK 2.5.2; новый клиент поддерживает старый сервер через явное переключение при 404.
- Запись пачки выполняется одним INSERT через json_each. События, дневной прогресс, баллы, версии состояния и отметки пересчёта согласованы транзакционно. Повторы используют прежние ID.
- Счётчики user_totals, week_points и weekly_best обновляются адресно SQL-триггерами. Рейтинг получает в SQL первые 200 строк, позицию пользователя и количество участников; история выдаётся страницами.
- Недельное обслуживание отделено в server/maintenance.js: Cron раз в минуту, ограниченные порции, возобновляемое заполнение сводок, ревизии задач weekly_dirty. Посещение экрана не закрывает недели и не пересчитывает всех пользователей.
- История согласия на участие защищает призы при задержанном запуске Cron. Сохранены версии правил, равные места, UTC+2 спортивной недели, личные часовые пояса, 15 секунд завершения и 7 дней допустимой синхронизации.
- Клиент сохраняет события в IndexedDB и отправляет их короткими пачками через 1,5 секунды. Завершение раунда сразу опустошает очередь. Устаревшая ревизия не отменяет подтверждённый прогресс.
- Диагностика — отдельные activity-log.js, diagnostics-panel.js и diagnostics.css. Панель закреплена внизу всех экранов; проверка и настройка сервера находятся внутри. Журнал текущего сеанса хранит последние 300 событий, поддерживает копирование и очистку. Записываются действия, сеть, модель, состояния тренировки, локальная очередь и ошибки; исходные запросы, имена, токены и координаты не журналируются.
- При старте камера прокручивается в видимую область: Chromium может замедлять кадры вне экрана. Алгоритм распознавания и его пороги не изменены.

## Измерения

Изолированная SQLite в памяти, Node.js, 1 000 синтетических пользователей и 52 недели истории, 5 измерений на сценарий. Согласованное исходное состояние подготовлено до измерений. Это диагностический эксперимент, а не оценка сетевых задержек, тарифа D1 или максимального числа пользователей.

| Сценарий | Ответ, байт: до → после | SQL-вызовы API: до → после | Локальное p50, мс: до → после |
|---|---:|---:|---:|
| Загрузка панели | 49079 → 4123 | 23 → 21 | 8775.1 → 4.24 |
| Одно повторение | 49166 → 605 | 25 → 10 | 6407.8 → 3.8 |
| Пачка из 10 | 49169 → 606 | 34 → 13 | 8105.98 → 2.83 |
| Пачка из 50 | 49171 → 609 | 74 → 10 | 6221.68 → 5.3 |

Счётчик SQL не включает операции внутри триггеров и не измеряет все просканированные строки. p95 в исходных JSON — максимум пяти прогонов; запуск среды и фоновая нагрузка могут влиять на время. Основной проверяемый эффект: отсутствие общего пересчёта в запросе сохранения и уменьшение его ответа приблизительно на 99% на этом наборе.

Полные результаты: [до](benchmarks/server-before.json), [после](benchmarks/server-after.json). Для текущей реализации: npm run benchmark:server -- --v2 --output work/benchmarks/after.json. Исходный замер повторяется тем же скриптом, скопированным в отдельный checkout main 2.5.2, без --v2.

## Проверки и границы

Проверяются старый и новый API, 100 событий в одной транзакции, повторная доставка, изоляция владельцев, курсоры с одинаковым временем, общий личный рекорд, поздние недельные начисления, неизменность призов, задержанный и параллельный Cron, сбой транзакции и продолжение задач, подтверждение старого недельного итога и переключение календаря во время запроса.

Отдельно проверены миграции, json_each, повторная запись, изоляция профилей, постраничная загрузка и scheduled в настоящем локальном runtime Workers с D1. Сборка Android проверяет пакет, версию, разрешения, ресурсы MediaPipe/WASM и APK-подпись. Браузерные сценарии используют синтетические положения тела; загрузка настоящей модели проверяется отдельно. Физический Samsung Galaxy S23 в среде не подключён.

Общие рейтинги читают небольшие агрегированные таблицы. Дополнительный распределённый кэш пока не введён: он добавил бы задержку актуальности и сложность исключения участников. Необходимость кэша следует проверять на реальном трафике. Старый APK по-прежнему получает полный ответ своего API — для уменьшения его трафика нужен новый клиент.

Локально прошли 164 unit/integration-теста и 39 браузерных сценариев (включая 4 проверки общей диагностики). Отдельный тест настоящей модели в текущем headless-исполнителе загрузил модель, но не завершил инференцию до таймаута. Тот же тест не проходит на исходном клиенте 2.5.2, извлечённом из прежнего APK и запущенном на отдельном стенде. vision.worker.js (137064 байт), WASM (11453626 байт) и модель (9398198 байт) побайтно совпадают с 2.5.2. Этот тест не засчитан как успешный; работу настоящего распознавания и GPU следует проверить на Samsung Galaxy S23. Пороги и алгоритм распознавания в выпуске не изменены.

## Тестовый выпуск

- APK 2.5.3: отдельный пакет com.movement.squat.staging, название «Движение Тест».
- Worker: movement-test-api-staging, отдельная D1 movement-test-app-staging.
- Адрес: https://movement-test-api-staging.rojoscarlos93.workers.dev.
- В новом тестовом приложении создаётся самостоятельный гостевой профиль. Профиль установленной основной версии относится к рабочему серверу.
- GitHub Actions проверяет код, браузерные сценарии, собирает и публикует APK в рабочей ветке, затем разворачивает staging. PR запускает проверки без публикации.
- Слияние в main и рабочий сервер — после проверки результатов. Для рабочего сервера нужны все миграции до публикации Worker; затем обновляется клиент. Удаление прежних таблиц и API в этот выпуск не входит.

## Возврат и эксплуатация

Миграция добавляет таблицы, индексы, триггеры и служебные колонки. Прежние события, награды и раунды сохраняются. Для возврата можно опубликовать совместимую версию 2.5.2 поверх обновлённой схемы, сохранив базу и отключив новые расписания вместе с Worker. Триггеры продолжают учитывать обычные записи старого API. При длительном возврате и последующем повторном включении новой версии потребуется сверить временную историю согласия; автоматический обратный откат SQL и удаление новых таблиц не предусмотрены.

Cron повторяет недоделанную работу с контрольной точкой. При большом накопленном долге личные сводки заполняются постепенно; спортивные места фиксируются при закрытии периода. Клиент показывает незакрытый период как предварительный. Первый перенос большой базы нужно проводить с тестированием миграции и контролируемым заполнением агрегатов до рабочего выпуска.

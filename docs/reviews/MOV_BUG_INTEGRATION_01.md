## Изменения интеграции и проверки

Версия package.json, корневых полей lockfile и src/config.js повышена до 2.6.1;
Android versionCode по существующей формуле — 20601. Принятые BE/FE blobs не менялись.
Задания/протокол телефона/реестр собраны в эту ветку. Сверены версии, зависимости,
отсутствие diff server/SQL/contracts/Android identity и git diff --check.

Frontend [CI 40560903759](https://github.com/rojoscarlos-cpu/APP-updated-version-/actions/runs/40560903759)
на b9ea8632 успешен: полный набор, типы/формат/синтаксис, build/dry-run, браузеры.
Backend передал адресные 4 readiness / 23 workouts-server / 90 deployment PASS;
точные команды и ограничения — в [отчёте](../releases/MOV-BUG-BE-01.md).
Эти результаты не выдаются за выполненные на общем новом source SHA.

Для общего SHA запланирован один штатный CI-прогон checks → signed Android.
Результат и artifact проверяются по фактическому run; до успеха CI/APK имеют статус
NOT_RUN/IN_PROGRESS, наличие этого документа само по себе не означает успешную сборку.
Повторных полных локальных прогонов перед CI не выполняется.

Коннектор не предоставляет workflow_dispatch, gh API заблокирован сетевым доступом,
локально нет JDK/SDK и signing key. Поэтому в backend.yml добавлено только условие
Android job после checks для push конкретно этой временной ветки. Переиспользуются
существующие android.yml и Actions signing secret; deploy.yml и публикация не меняются.
Это условие не включает APK для остальных временных веток.

## Приёмка APK и допуск телефона

После успешного CI получить приватный Actions artifact и проверить checksum,
package com.movement.squat.staging.ui, 2.6.1 / 20601, pinned certificate
122721cc9aa1600dca3ba86f4318f0e3c43c3c4b562a5c8d3114ea4194dfc0de,
source SHA/dirty=false в JSON и внутри APK, локальные ML-ресурсы и manifest.
Не использовать APK ветки Frontend версии 2.6.0 или прежний public APK.

На телефоне допустимо проверить обновление без потери данных, копирование
диагностики и понятное состояние недоступного сервера. Полный сценарий программ
и восстановление зависшей записи требуют совместимого API, подтверждённого
авторизованным checker и фактическим статусом сервера/0005.

Восстановление: прежний профиль/API → «Проверить снова» → прежние UUID → ack
очереди → прежний pendingEnd → подтверждённый aborted → новая программа.
Не очищать данные, не выходить из профиля и не удалять приложение ради обхода.
Запись за пределами окна доставки не объявлять восстановленной этим исправлением.

Слияние main, remote-миграции и публикация требуют отдельной прямой команды
владельца; запрос подготовить тестовый APK её не заменяет. Эти действия здесь
не выполняются. Следующий функциональный этап остаётся отложен до приёмки.

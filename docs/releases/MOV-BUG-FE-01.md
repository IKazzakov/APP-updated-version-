## Поведение до и после

До исправления онлайн-start записывал active до проверки поддержки программ.
При 404 запись оставалась, abort сохранял pendingEnd, но каждый sync снова
получал 404. После reload другая программа блокировалась без понятного пути
восстановления; журнал скрывал маршруты под `other`.

Теперь перед новым онлайн-start выполняются catalog/activity GET с существующими
runtime-парсерами. Отсутствие маршрута обнаруживается до очистки предыдущего
закрытого результата, новой active-записи, sync POST и камеры. Упакованный каталог
не служит доказательством готовности сервера. NETWORK/TIMEOUT, auth/profile,
невалидный JSON и конкретный WORKOUT_NOT_FOUND не маскируются несовместимостью.

Готовность API отделена от ошибки доставки: `unknown/checking/ready/unsupported`
и `availabilityError` не стирают `error` завершения при успешном чтении XP.
Параллельные проверки объединяются для текущего API/profile/epoch; поздний ответ
прежнего сеанса не меняет новый профиль и не запускает следующий GET от его имени.
Известный маршрутный 404 инвалидирует готовность; навигация больше не порождает
повторные sync POST. Явное «Проверить снова» перепроверяет GET и доставляет журнал.

Active до 24 часов предлагает явное продолжение или досрочный итог; после 24 часов
продолжение недоступно. При pendingEnd показано «Завершение ожидает подтверждения»
и повтор сохранения. При несовместимости видны причина и «Проверить снова».
До ack нельзя начать конфликтующую программу; после подтверждённого abort другая
программа доступна без reload. Ни reload, ни retry, ни подтверждение не включают
камеру: требуется отдельное нажатие запуска.

Ни одна неподтверждённая запись не удаляется для разблокировки. `synced=false`
не трактуется как отсутствие серверной записи. UUID выполнения/событий,
pendingEnd, порядок локальных writes → event ack → end, sending, epoch/CAS
сохранены. Потерянный ответ повторяется с прежними UUID без повторного XP.
Существующая подготовка/продолжение offline сохранена; известный 404 не скрывается
offline-успехом. Scope, формат и реализация storage/offline не менялись.

## Автоматическая диагностика

Существующие `version` и `report: "squat-support-v1"` сохранены. Дополнительно:

```text
build: {version, versionCode, sourceSha, dirty}
apiBaseUrl: безопасные фактические origin+pathname либо null
```

SHA вычисляется из фактического checkout HEAD при сборке; dirty — из Git status,
включая неигнорируемые untracked-файлы. Версии package/config должны совпадать;
versionCode использует формулу Gradle. Один snapshot используется в Vite-клиенте,
`build-metadata.json` и `app-debug.apk.json`. В нём нет вручную заданного SHA или
сведений, загруженных из метаданных другого APK. Dev без Git сообщает null/null.

Для подписанного APK требуются полный SHA и чистые исходники до штатных временных
изменений config/strings и удаления старого downloadable APK. Snapshot передаётся
дочерним сборкам; устаревший SHA, несовпадение версии и новые изменения исходников
останавливают выпуск. В упаковщик добавлены проверки versionCode через aapt,
метаданных staging-клиента и фактического JSON внутри APK через JDK jar.
Сам APK в этой frontend-задаче не собирался.

Адрес API читается синхронно при создании отчёта из текущего getApiBaseUrl();
web `/api` разрешается относительно origin. Credentials, query и hash не попадают
в поле; небезопасный адрес даёт null. Clipboard и ручной textarea используют
один reportText до входа/камеры, без сети; очистка журнала сохраняет build-данные.
Это сведения клиента, а не подтверждение версии/готовности сервера.

ActivityLog получает только фиксированные `workouts.catalog/sync/finish/abort/history`,
`activity`, workout action/error-коды. UUID, query/hash, тела, credentials, имена,
landmarks и сырые URL не копируются в события.

Unit-регрессии покрывают preflight обоих GET до записи/POST, разделение ошибок,

Браузер использует реальный клиент, локальный API/изолированную SQLite и настоящую
IndexedDB. Старую active/synced=false/events=[]/pendingEnd=abort запись загружает
после reload: 404 и навигация не меняют её и не создают POST. После восстановления
тестового API явный retry выполняет sync → abort с прежней идентичностью/intent;
следующая программа запускается без reload. Камера запрашивается только после
явного нового старта. Распознавание здесь синтетическое, не физическое.

Diagnostics-сценарий до гостевого входа отключает сеть: clipboard точно равен
textarea, build совпадает с встроенным JSON и Git HEAD, версия/code — с package,
API — с текущим origin. Принудительный отказ clipboard включает ручное копирование;
очистка журнала сохраняет сведения. Unit отдельно проверяет смену адреса,
удаление секретов/query/hash и неизвестный dev checkout.

Для повторения целевых браузеров: запустить `tests/browser-server.mjs` с
`TEST_AUTH_MODE=device`, задать `TEST_ORIGIN` и соответствующий порт,
`CHROMIUM_PATH`, `NODE_PATH` к playwright-core. Затем вызвать два указанных
browser-файла с их адресными флагами. Без флагов прежние сценарии продолжают
выполняться вместе с новыми. Автоматический CI при push сохраняет штатный набор;
полный набор вручную повторно не запускался.

## NOT_RUN, ограничения и передача

- **NOT_RUN:** ручной полный npm test/browser:all, backend dry-run и APK.
  Полный контрольный прогон и одна APK-сборка предназначены общему кандидату.
- **NOT_RUN:** Android manifest/JSON/checksum именно нового APK, установка поверх
  2.6.0, диагностика установленного бинарника, физическая камера/FPS/нагрев,
  восстановление данных телефона. Нужны финальная сборка и проверка устройства.
- **NOT_RUN:** авторизованная проверка опубликованного workout API и причины 404,
  remote-миграции и deploy. Локальный тест не доказывает готовности основного Worker.
- Сетевой сбой после успешного GET всё ещё может оставить новый локальный журнал:
  это безопасная сохраняемая работа, доступная для retry, а не основание удалить её.
- Запись вне существующего серверного окна доставки не объявляется восстановленной;
  ограничения 24 часов/7 дней не изменены.

Backend: подтвердить совместимость фактического API в своём пакете, включая
маршруты и миграцию. Ошибку опубликованного Worker этот клиентский PR не устраняет.
Тимлид: интегрировать разрешённым порядком оба PR, согласовать итоговую версию,
зафиксировать общий source SHA и выполнить один финальный прогон/подписанную сборку.
Сверить встроенный build, JSON и manifest; затем на телефоне проверить сохранённый
API-base и доставку прежней записи. Не очищать данные и не выходить из профиля
для обхода блокировки. Восстановление: совместимый API → прежние UUID → ack
очереди → прежний pendingEnd → подтверждение → следующая программа.

Main merge, публикация, remote-миграции и независимая проверка другим разработчиком
в этой задаче не выполнялись и не назначались.

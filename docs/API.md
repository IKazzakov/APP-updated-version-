# Серверный протокол MVP

Все API возвращают JSON с `Cache-Control: private, no-store`. В production
платформа Sites завершает вход ChatGPT и передаёт проверенный
`oai-authenticated-user-id`. Без него API отвечает `401`. Этот заголовок
нельзя подменять в клиенте; локальные тестовые личности задаются только
отдельным тестовым сервером, который не входит в сборку приложения.

Все POST требуют `Content-Type: application/json` и `Origin` того же сайта.
Авторизация проверяется на каждой операции. Пользователь видит свою личную историю и только свои дуэли. Общие рейтинги раскрывают минимальные показатели участвующих профилей, не сохранивших отказ. Получатель секретной ссылки
до принятия видит только имя автора, версию правил и доступность приглашения.

Общий формат ошибки:

```json
{"error":{"code":"ACTIVE_ROUND","message":"У вас уже идёт минутный раунд. Завершите его на другом устройстве или вкладке."}}
```

Сообщения — константы. SQL, тела запросов, ссылки, имена, токены и координаты
не выводятся в технический журнал. Неизвестные поля, включая координаты,
отклоняются.

## Профиль и состояние

- `GET /api/state` → `{profile,today,days,points,last7,rounds,activeRound,competitions,weekly,serverNow,rulesVersion}`.
- `POST /api/profile` с `{displayName,timeZone,rankingsEnabled?}` → `{profile,state}`.

`profile` — `{id,displayName,timeZone,rankingsEnabled}`, либо `null` до создания профиля.
Имя — от 1 до 40 символов, не email из авторизации. Часовой пояс проверяется
по IANA и записывается только при первоначальном создании. Повторный вход с
другого устройства может изменить имя, но сохраняет первоначальный пояс.

`today` — `{date,count,goal:10,completed}`. `days` содержит
`{date,count,completed}`; `points` — сумма `daily_rewards` и `weekly_bonuses`; `last7` — число
выполненных дат в интервале сегодня минус 6 дней — сегодня, в поясе профиля.
`rounds` содержит только завершённые личные и соревновательные раунды;
прерванные попытки остаются в БД для лимитов, но не входят в эту историю.
Для сравнения клиент дополнительно отбирает раунды совместимой версии правил.

## Повторения и дневная награда

`POST /api/repetitions`:

```json
{"events":[{"id":"UUID","occurredAt":"ISO-8601","roundId":"UUID","elapsedMs":10234}]}
```

Обычная тренировка не передаёт `roundId` и `elapsedMs`. `occurredAt` также
принимает целое UTC-время в миллисекундах. Размер пачки — от 1 до 100.
Событие должно быть не старше 7 дней и не более чем на 5 секунд в будущем
относительно сервера. Для минутного раунда время нормализуется клиентом по
`serverNow`/`startsAt`; `elapsedMs` должно быть целым в `[0,60000)` и совпадать
с UTC-временем с допуском 5 секунд. Событие нельзя привязать к чужому раунду.

Ответ: `{accepted,duplicate,state}`. Повтор с тем же `(userId,eventId)` ничего
не меняет. Все события пачки и SQLite-триггеры выполняются одной транзакцией.
Триггер увеличивает дневной прогресс и при достижении 10 создаёт награду с
уникальным ключом `(userId,localDate)`. Повтор запроса или вторая вкладка
не увеличивают ни число повторений, ни награду повторно. Дополнительные
приседания увеличивают дневное число, но не дневную награду.

Повторения прерванного раунда разрешено безопасно доставить позднее для
дневного задания, если они произошли до остановки. Они не делают раунд
завершённым и не попадают в рекорды. События после остановки отклоняются.

## Минутные раунды

- `POST /api/rounds/start` с `{requestId:"UUID",kind:"personal"}` либо
  `{requestId:"UUID",kind:"competition",competitionId:"UUID"}` → `{round,serverNow}`.
- `POST /api/rounds/:id/finish` с `{}` → `{round,state}`.
- `POST /api/rounds/:id/abort` с `{}` → `{round,state}`.

Раунд — `{id,kind,status,competitionId,rulesVersion,startsAt,endsAt,finishedAt,count}`.
Все отметки времени — UTC миллисекунды; `endsAt-startsAt` всегда `60000`.
Статусы — `active`, `completed`, `aborted`.

`start` вызывается после подготовки и обратного отсчёта. Повторный
`requestId` возвращает ту же попытку без нового расхода. Один пользователь
может иметь только один активный минутный раунд; это ограничено частичным
уникальным индексом БД и условным INSERT, включая разные устройства.
Время задаёт сервер; число обработанных кадров на него не влияет.

Перед завершением клиент доставляет очередь повторений и только затем
запрашивает `finish`. Сервер не подтверждает результат раньше `endsAt`.
Для передачи результата по сети отведено 15 секунд после конца таймера;
это не дополнительное время упражнения. Поздние повторения не допускаются.
После этого активный раунд автоматически помечается прерванным. Он никогда
не превращается в завершённый только из-за истечения времени. При
перезагрузке клиент сверяет `activeRound` с маркером этой вкладки и явно прерывает свою попытку. Новая вкладка не прерывает попытку другого устройства;
не восстанавливая таймер. Повтор завершения или прерывания идемпотентен.

## Соревнования

- `POST /api/competitions` с `{requestId:"UUID",token:"64 hex characters"}` →
  `{competition,invitationToken}`. Клиент создаёт 32 случайных байта через
  `crypto.getRandomValues`; при повторе запроса сохраняет тот же token.
- `POST /api/invitations/preview` с `{token}` →
  `{competitionId,creatorName,status,rulesVersion,canAccept}`.
- `POST /api/invitations/accept` с `{token}` → `{competition,state}`.

База хранит только SHA-256 токена. Ссылка использует фрагмент браузерного
адреса, который не отправляется серверу в URL. Токен передаётся телом POST;
он не должен попадать в диагностику. Повтор создания возвращает то же
соревнование. Сам автор принять приглашение не может. Условный UPDATE
позволяет занять место только одному другому профилю; повтор принятия тем же
профилем возвращает уже принятое соревнование без сдвига срока.

Соревнование:

```js
{
  id, rulesVersion, status, createdAt, acceptedAt, expiresAt,
  participants: [{role:'creator'|'opponent',name,isYou,best,attemptsUsed,attemptsLeft,activeAttempt}],
  result: null | {type:'tie'|'winner'|'not_held',winner:null|'creator'|'opponent'},
  canStart, canCancel, preliminary
}
```

До принятия статус `invited`, попытки недоступны. После принятия — `active`
на 24 часа. Сервер при каждом запуске проверяет участника, версию правил,
оставшиеся минимум 60 секунд, число использованных попыток `<3` и отсутствие
другого активного раунда. Любая запущенная попытка, включая прерванную,
расходует лимит. Подготовка камеры и обратный отсчёт лимит не расходуют.

После истечения срока либо после использования всех трёх попыток обоими
участниками и завершения их активных раундов определяется итог. Если
последняя попытка завершилась у самой границы суток, состояние `settling`
остаётся предварительным максимум на время сетевой доставки (15 секунд).
Новых попыток в это время нет. Затем статус `finished`. Итог берёт лучший
завершённый результат каждого; равенство — ничья; отсутствие завершённого
результата хотя бы у одного — «Не состоялось». Баллы в сравнении
не участвуют. Одна строка раунда используется и соревнованием, и личной
историей, поэтому дубликат результата не создаётся.

## Граница доверия

Телефон определяет приседания по локальному видео. Сервер не получает
изображения, видео, звук или координаты и не доказывает физическое выполнение.
Он проверяет вход и владельца данных, часовой пояс/границы дней,
идемпотентность, атомарность наград, сроки, лимиты и статусы раундов.
Это дружеские соревнования, а не система защиты от подмены результата.


## Недельные рейтинги · 2.2.0

`rankingsEnabled` — boolean, с версии 2.3.0 по умолчанию true для существующих и новых профилей. Галочка UI «Не участвовать» инвертирует это поле. Отсутствующее поле при обновлении имени сохраняет текущую настройку, в том числе отказ. Перед изменением согласия сервер закрывает уже истёкшие периоды: включение не добавляет участника в закрытый рейтинг. Выключение скрывает и исторические строки через текущую настройку профиля, сохраняя снимки и выданные награды.

`GET /api/leaderboards?type=result|points&period=week|all&week=YYYY-MM-DD`:

- По умолчанию `type=result`, `period=week`, текущая серверная спортивная неделя. `all` разрешён только для points. Неделя — валидная дата понедельника существующего периода, не раньше активации.
- Ответ: `{type,period,week,periodInfo,serverNow,timeZone,pointsMayUpdate,entries,totalParticipants,you}`.
- `periodInfo`: `{week,startsAt,endsAt,rulesVersion,closed}`. `timeZone` — `Africa/Johannesburg`.
- Строка `entries` и `you`: **только** `{place,name,value,isYou}`; нет ID входа, почты, раундов, координат или приглашений. До 200 строк; личное место возвращается отдельно даже за пределами первой страницы.
- result: `MAX(count)` завершённых положительных минут personal/competition с точным совпадением версии и `ends_at` в полуоткрытом интервале. Активные, прерванные, нулевые и несовместимые раунды исключены. `RANK() OVER(ORDER BY score DESC)` даёт места с пропусками; имя/внутренний ID используются только для устойчивого порядка строк.
- points/week: сумма дневных наград с `local_date` в выбранной неделе плюс бонусы с этим ID недели; all — все дневные награды и бонусы, включая старые дневные баллы. Здесь нет спортивной фильтрации по версии: баллы — самостоятельный баланс. Нулевые балансы участвующих также отображаются. Награды за место по баллам нет.

`weekly` в личном `/api/state`:

```js
{
  activationWeek, sportsWeek, timeZone, periods: [periodInfo],
  yourWeek: {week, dates:[{date,completed,past,today}], completedDays, remaining,
    possible, canSyncPast, points:{completedDays,daily,fullWeek,sport,total}},
  places:{result:null|{place,value},points:null|{place,value}},
  summaries:[{week,completedDays,best,place,participated,points:{daily,fullWeek,sport,total},
    revision,seen,updatedSinceSeen,rulesVersion,pointsMayUpdate}]
}
```

`yourWeek` — календарная неделя **профиля**. `sportsWeek`, места и общая таблица — неделя **UTC+2**. `possible=false` означает пропущенную неподтверждённую дату, не обещание восстановить её новыми повторениями. `last7` остаётся прежним скользящим интервалом. Все вычисления серверные; клиент только форматирует даты и отображает оставшееся время по серверным часам. Клиентский ноль на обратном времени не закрывает период.

`POST /api/weeks/seen` с `{week,total}` → `{state}`. Обновляется только собственная сводка с текущей подтверждённой суммой `total`; чужой userId не принимается. `seen_at` сохраняется навсегда, `seen_total` позволяет отметить позднее изменение суммы. Изменившаяся между чтением и подтверждением сумма не помечается просмотренной ошибочно. Повтор запроса безопасен.

### Хранение, восстановление и транзакции

Добавочная миграция `0001_weekly_rankings.sql` не меняет применённый `0000_squat_mvp.sql`, `daily_rewards CHECK(points=10)` и исходный триггер. Новые таблицы:

- `weekly_settings`: постоянные activation timestamp и Monday ID, INSERT ON CONFLICT DO NOTHING;
- `weekly_periods`: границы, закреплённая версия правил, закрытие;
- `weekly_participants`, `weekly_standings`: снимок участия и итоговых мест/чисел;
- `weekly_bonuses`: full_week / sport_place, user, week, points, awarded_at, уникальное basis; PK `(user_id,week,type)`;
- `weekly_summaries`: сохраняемые личные итоги, revision и отметка просмотра.

Недельные бонусы выдаются начиная с activation_week; прежние дневные баллы сохранены. Семь различных local_date Пн–Вс дают full_week +20 независимо от участия. `last7` для бонуса не используется. Награда sport_place: 1 →20, 2 →10, 3 →5. При разделённом месте каждый получает полную награду. Один sport_place на человека и неделю, одно full_week на человека и неделю. Дневные награды в этот журнал не копируются.

На следующем успешном API-обращении сервер создаёт пропущенные периоды после активации и закрывает все подходящие недели для всех участников. Требуется `now > ends_at + DELIVERY_GRACE_MS` (15 секунд). Одна D1 batch-транзакция: прерывание истёкших active, фиксация участия и RANK, INSERT наград, closed_at. Ошибка откатывает всё закрытие, повтор восстанавливает его; уже закрытые спортивные награды не пересчитываются.

Поздние repetition_events в пределах EVENT_RETENTION_MS (7 дней) по прежнему триггеру могут дополнить daily_rewards прошлой недели. Сервер восстанавливает её full_week и сводку, сохраняет исходный ID недели и seen_at. Баллы изменяются, спортивные места/награды — нет. `pointsMayUpdate` сообщает о возможном дополнении: учитывается срок доставки и консервативный двухдневный запас на разные пояса профилей. Для all-time баланс продолжает обновляться всегда. Нет клиентского начисления или зависимости от открытой страницы в момент границы.


## Отмена приглашения и участие по умолчанию · 2.3.0

`POST /api/competitions/:id/cancel` с `{}` → `{competition,state}`. Только автор, только пока opponent_id IS NULL. Возвращается status=cancelled и canCancel=false. canCancel=true выдаётся автору непринятого действующего приглашения. Отмена повторяема без дублей; строка соревнования, история и награды не удаляются, попыток нет. Чужому профилю — 404, уже принятому приглашению — 409 INVITATION_ACCEPTED. Неизвестные поля и неправильный origin отклоняются как прежде.

Preview отменённой ссылки возвращает status=cancelled и canAccept=false. Accept и start для такой ссылки/дуэли отклоняются с INVITATION_CANCELLED. Условные UPDATE для accept и cancel проверяют оба признака: opponent_id IS NULL и cancelled_at IS NULL. При гонке выигрывает только одно действие. Старый create_request_id не воскрешает отменённый вызов; для нового используется новый запрос.

Добавочная миграция `0002_ranking_defaults_duel_cancel.sql`: profiles.rankings_excluded (NOT NULL DEFAULT 0), competitions.cancelled_at (nullable). Старые поля и строки не удаляются. По прямому запросу владельца все существующие профили, включая ранее не включавшие участие, теперь включены по умолчанию. Старый rankings_enabled не участвует в фильтрации. В API сохраняется положительное поле rankingsEnabled; эффективное значение = !rankings_excluded. Новый отказ пользователя сохраняется, обычная смена имени/повторное развёртывание его не сбрасывают. Исторические закрытые награды и места не перераспределяются.

Клиент не привязывает загрузку таблицы к каждому render/state.serverNow. Запросы при открытии, смене фильтра, ручном обновлении или содержательном изменении данных; одинаковые запросы в полёте объединяются. При фоновом/ручном обновлении той же таблицы строки остаются видны; сетевой сбой явно помечает их как предыдущие данные. Это не изменяет серверные сроки и начисления.


## Оптимизированный API v2 (2.5.3)

Индивидуальная Bearer-сессия и правила записи остаются прежними. Старые маршруты /api/* продолжают обслуживать APK 2.5.2. Новый клиент сначала использует /api/v2/dashboard; при 404 NOT_FOUND/API_NOT_FOUND переключается на старый API. Сетевые ошибки не маскируются переключением.

- POST /api/v2/repetitions: прежние события; ответ accepted, duplicate, state. state.partial=true; только профиль, today, последние 8 дат, last7, points, bonusPoints, activeRound, version, serverNow, rulesVersion. Без истории, соревнований и рейтинга. До 100 событий; транзакционная запись через json_each с возвратом фактически вставленных ID.
- GET /api/v2/dashboard: текущие показатели, 2 последних совместимых завершённых раунда, общий личный рекорд, до 12 периодов и 4 личных недельных итогов. История соревнований загружается отдельно.
- GET /api/v2/history/rounds?limit=50&cursor=...: завершённые раунды, сортировка finished_at DESC,id DESC.
- GET /api/v2/history/progress?from=YYYY-MM-DD&to=YYYY-MM-DD&limit=50&cursor=...: дневной прогресс; диапазон до 366 дней.
- GET /api/v2/history/weeks?limit=50&cursor=...: личные недельные итоги.
- GET /api/v2/competitions?limit=50&cursor=...: принадлежащие пользователю соревнования; сортировка created_at DESC,id DESC; максимум 50 записей за страницу.
- Остальные действия /api/v2/profile, /api/v2/rounds/*, /api/v2/invitations/*, /api/v2/competitions/* и /api/v2/weeks/seen используют прежние входные поля и ограниченные ответы. Подтверждение старого недельного итога дополнительно возвращает затронутый итог, даже если он старше четырёх последних.

Страница возвращает items, nextCursor (null на последней странице), limit, serverNow. Для истории максимум 100 записей. Курсор — проверяемый base64url JSON с типом списка и последним ключом, без идентификатора владельца. Владельца всегда определяет авторизация, а не курсор.

version — монотонная ревизия пользовательских данных. Компактные ответы объединяются с уже загруженными страницами; более старая ревизия не заменяет подтверждённый прогресс. bonusPoints — общий подтверждённый объём недельных наград, чтобы загрузка старой страницы не выглядела новой выдачей бонуса.

Недельное обслуживание запускает scheduled-обработчик раз в минуту; локальный Node.js использует тот же модуль. Один запуск ограничивает закрываемые периоды и число личных сводок. weekly_dirty хранит ревизию задачи; условное удаление сохраняет работу, поступившую во время обработки. Согласие на участие фиксируется во временной истории и оценивается на границе окончания недели плюс 15 секунд. При задержке Cron API показывает незакрытый период, а правила допустимого времени раунда продолжают действовать.

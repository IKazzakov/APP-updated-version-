# Роль: Frontend

Ты — frontend-разработчик приложения «Движение», счётчика приседаний через камеру. Общайся с владельцем на русском. Отвечай за клиентский интерфейс, интеграцию по API-контракту, типизацию клиентских границ, сохранение локальных данных и корректный жизненный цикл экранов.

## Текущий стек

- ES Modules, JavaScript и постепенно внедрённый TypeScript; Vite собирает клиент.
- React, Vue, UI-kit, CSS-framework и библиотеки глобального состояния в текущих зависимостях отсутствуют. Интерфейс использует HTML-фрагменты `*.html?raw`, DOM и CSS. График прогресса реализован на SVG, наложение скелета — на Canvas.
- Capacitor предоставляет Android-оболочку и нативный HTTP. Версии зависимостей закреплены в `package.json` и lockfile; не заменяй их по памяти.
- MediaPipe Pose Landmarker Full работает с локальными моделью и WASM через существующий движок и Web Worker. Модель и пороги не относятся к обычному изменению UI.
- TypeScript использует `strict`, `noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly` и `noEmit`. Разрешён импорт JS, но `checkJs:false`: старый JS не стал полностью строго типизированным. Границы существующих модулей описаны соседними `.d.ts`.

Новые клиентские модули и контракты пиши на TypeScript. Переводи существующий JavaScript в пределах согласованной задачи, сохраняя поведение. Не вводи новый UI-framework, глобальный store или HTTP-клиент без архитектурной необходимости в задаче.

## Экран, состояние и lifecycle

Экран получает собственный `root` и [FeatureContext](../../src/shared/feature.ts). Используй переданные команды `navigate`, `chooseMode`, `openProfile`, `openLeague`, `refresh`. Не ищи DOM другого экрана через `document` и не импортируй его контроллер ради перехода.

Корни экранов создаются один раз. Фоновая синхронизация обновляет представления и сохраняет введённый текст, фокус и существующий `video`. Не пересоздавай формы или камеру при каждом ответе сервера. `render` отображает данные; запросы запускаются пользовательскими действиями или операциями lifecycle.

Изменяй общее подтверждённое состояние через `AppStore.apply/page/reset` и методы `SessionService`. Не присваивай поля общего состояния из экранов. Подписки и фоновые ответы должны учитывать epoch/generation: ответ прежнего сеанса не меняет новый профиль, даже если пользователь вернулся в ту же учётную запись.

При добавлении экрана создай модуль с шаблоном, представлением/контроллером и стилями, затем зарегистрируй фабрику в `app/registry.ts`. Фабрика возвращает `root`, `render` и необходимые `activate`, `refresh`, `deactivate`, `destroy`. Освобождай собственные ресурсы; общие слушатели и интервалы оформляй через [Lifecycle](../../src/shared/lifecycle.ts).

Переход с тренировки и уход приложения в фон должны сохранять существующий порядок остановки/прерывания, освобождения camera tracks, lease, wake lock и звука. Не допускай позднего восстановления потока после отмены разрешения камеры. Камера и подготовка автоматического старта активируются действием пользователя, а не открытием страницы, вкладки или получением API-ответа.

HTML и CSS находятся рядом с соответствующей функцией. Используй стили с областью `:where([data-feature='имя'])`, сохраняй общую мобильную типографику, место под диагностику и safe-area устройства. Пользовательский текст экранируй через общие DOM-функции; имена и приглашения не должны превращаться в исполняемую разметку.

## Интеграция по API-контракту

Штатный путь данных: экран → `SessionService` → проверяемый API-клиент → `createDataClient` → transport. При добавлении вызова изучи [API.md](../API.md), тип запроса/ответа в [api.ts](../../src/shared/contracts/api.ts) и соответствующий parser в [validate.ts](../../src/shared/contracts/validate.ts). Не импортируй в browser-контракты Node.js, D1, секреты или серверную реализацию.

TypeScript-тип не проверяет внешний JSON. Ответ проверяется во время исполнения до изменения состояния. Некорректный ответ даёт `API_RESPONSE_INVALID` и сохраняет ранее подтверждённые данные. Совместимые дополнительные поля разрешены. Изменение API должно включать согласованные документацию, типы, валидаторы и контрактные тесты в том же PR.

Различай полный snapshot v1, компактный dashboard v2, частичное подтверждение записи v2 и страницу истории. `state` согласуется с `v2/dashboard` через существующий data client. Не заменяй состояние коротким ack целиком. Сохраняй уже загруженные страницы и не применяй меньшую ревизию. Календарные даты передаются как `YYYY-MM-DD`, серверные timestamps — миллисекунды Unix, `occurredAt` повторения — ISO timestamp.

Fallback v2 → v1 допускается только при ожидаемом `404 NOT_FOUND/API_NOT_FOUND`. Не маскируй сетевую ошибку переключением версии API. Сохраняй обработку ошибок через `ApiError` и текущую диагностику. Пользователь должен видеть отсутствие связи или неподтверждённое сохранение; не показывай выдуманный успешный результат.

До явного гостевого входа `401 DEVICE_AUTH_REQUIRED` — ожидаемое состояние. Не создавай новую сессию фоновым запросом только ради устранения этого ответа. Имя не является идентификатором или credential. Public Worker использует индивидуальный device-token; тестовые способы идентификации не должны проникать в публичный клиентский сценарий.

## Надёжное сохранение и правила тренировки

- Сначала запиши повторение локально с устойчивым UUID, затем отправляй. Потерянный ответ повторяется с тем же ID. `Outbox` использует IndexedDB; ошибка локальной записи должна быть видна пользователю, а не заменяться памятью с обещанием надёжного сохранения.
- Перед `finish/abort` дождись всех локальных записей, отправки и подтверждённого опустошения очереди. Не заверши попытку раньше последнего повторения ради быстрого UI.
- Очереди, device-secret, active-round и finalization markers привязаны к API-base и профилю. Не переименовывай ключи хранения и не меняй их область без согласованного сценария миграции.
- Смена профиля закрывает прежнюю очередь до смены учётных данных. Неподтверждённые события не удаляются и не отправляются от нового владельца. Не очищай очередь при навигации, потере сети или ошибке валидации; сохраняй штатный явный повтор.
- `RoundPersistence` восстанавливает неподтверждённое завершение и прерывание после reload. Используй существующий механизм, включая защиту от чужого активного раунда из другой вкладки.
- В дуэли выбирается лучшая из трёх попыток. Положительный подтверждённый счёт раннего abort учитывается у обоих участников, но раунд остаётся `aborted`. Личный рекорд и спортивный рейтинг требуют `completed` за полные 60000 мс. Отображение UI не должно менять эти правила.
- Не меняй модель Full, WASM, алгоритм, пороги или начисления в обычной UI-задаче. Если задача прямо затрагивает их, отдельно зафиксируй критерии проверки и согласованное влияние на контракт/результаты.

## Android и один сервер

Единственный основной API на момент создания инструкции: `https://movement-test-api-staging.rojoscarlos93.workers.dev/api`. Суффикс `staging` — технический. Web использует `/api`; Android использует текущий native API-base и Capacitor HTTP, сохраняющий нужные `Origin` и `Authorization`.

Пакет установленного приложения — `com.movement.squat.staging.ui`, название — «Движение Тест UI». Сохраняй действующий signing key, пакет и адрес ради обновления без потери профиля. Не создавай новый пакет, ключ или сервер, чтобы обойти ошибку сборки. Не переписывай сохранённый пользовательский адрес молча. Смена API изолирует credentials, очереди и раунды; данные другого сервера автоматически не переносятся.

Источники сборки и проверки: [capacitor.config.json](../../capacitor.config.json), [android/staging-signing.json](../../android/staging-signing.json), [ANDROID_SIGNING.md](../ANDROID_SIGNING.md), [ANDROID_TESTING.md](../ANDROID_TESTING.md). Локальная APK-сборка требует JDK 21, SDK 36, Build Tools 36.0.0 и закреплённый ключ. Команда `build:apk:staging` сохранена для совместимости, отдельную инфраструктуру она не создаёт. Секреты и незашифрованные закрытые ключи в git и сообщения не добавляй.

## Диагностика и приватность

Диагностика подключается один раз вне экранов и доступна на каждом из них. Управление подключением к серверу остаётся внутри неё. Не создавай независимую панель подключения в отдельном экране.

В API и очередь передаются сведения о повторении, а не видео, звук или координаты тела. В журнал и отчёт не добавляй credentials, токены, имена, invitations, кадры или landmarks. Сохраняй существующие безопасные поля событий и ограничение журнала.

## Проверки и готовый результат

Проверки выбирай по реальному изменению. Основные команды и их точная реализация находятся в [package.json](../../package.json), [checks.yml](../../.github/workflows/checks.yml) и [scripts/test-browser.mjs](../../scripts/test-browser.mjs):

```sh
npm run typecheck
npm run format:check
npm run lint
npm test
npm run build
npm run backend:validate
npm run test:browser:all
```

`backend:validate` — dry-run без публикации. Браузерным тестам нужны Chromium/Chrome и `playwright-core`; пути задаются `CHROMIUM_PATH` и `NODE_PATH`. Используются отдельные SQLite, тестовые профили и искусственные положения тела. Для небольшой обратимой правки не придумывай тест, повторяющий реализацию; проверь соответствующий пользовательский сценарий. Для изменения auth, очереди, lifecycle или контракта требуются проверки затронутых гарантий и регрессий.

Перед выпуском проверь первый вход, сохранение профиля после перезапуска, камеру, навигацию без лишних потоков/запросов, offline/retry, прерывание раунда, ранний стоп дуэли, пагинацию, узкую и широкую компоновку и общую диагностику. Реальные движения, точность, звук, FPS и нагрев Galaxy S23 подтверждаются на устройстве; headless-сценарий не доказывает этих свойств.

Работай в отдельной временной ветке и передавай результат через PR. Слияние `main`, remote-миграции и публикация требуют прямой команды владельца соответствующей задачи; наличие workflow или старое разрешение на другой выпуск не заменяет её. Не меняй исходный репозиторий `Test`. В разрешённой задаче самостоятельно доводи реализацию и проверки до reviewable результата, не останавливайся на общем плане.

Для передачи результата укажи пользовательское поведение до/после, затронутые модули и контракты, выполненные проверки с результатами, реальные ограничения, ветку/PR и следующие действия другой роли, если они требуются. Не объявляй неподтверждённые проверки успешными и не переносись молча к другим областям проекта.

## Что установлено, а что ещё требует подтверждения

Владелец сообщает: незавершённую программу нельзя продолжить/отменить, остальные
программы не запускаются. В присланном журнале GET dashboard успешен, другие GET/POST
возвращают HTTP 404 с кодом NOT_FOUND. Время фрагмента — 2026-10-27T17:14–17:15Z
(19:14–19:15 Africa/Johannesburg).

В [activity-log.js](../../src/activity-log.js) маршруты workouts/activity отсутствуют
в безопасном перечне: поэтому журнал превращает их в other, а ряд новых ошибок —
в UNKNOWN_ERROR. По одному фрагменту нельзя установить точный URL неудачного запроса.

Код текущей интеграции содержит новые маршруты. Основная гипотеза — APK с программами
обращается к старому Worker или другой фактической версии API. Это не подтверждённый
диагноз опубликованного сервера: read-only чтение его /api/health инструментом
Тимлида оказалось недоступно. SHA установленного APK и его фактический сохранённый
API-base пока не получены. Отсутствие маршрута и отсутствие миграции — разные случаи:
само по себе отсутствие таблиц 0005 не доказывает NOT_FOUND и может давать SERVER_ERROR.

Тимлид выполнил один изолированный сценарий на настоящем WorkoutsService из базы:
подставлены долговременное по смыслу тестовое хранилище между двумя экземплярами
сервиса и transport, всегда возвращающий ApiError('NOT_FOUND',404). Это не проверка
реальной IndexedDB, камеры или опубликованного Worker. Получено:

```text
start: NOT_FOUND 404
local after start: unfinished=true, synced=false, events=0, status=active
abort: NOT_FOUND 404
local after abort: unfinished=true, pendingEnd=abort, status=active
new program after reload: Сначала продолжите или завершите текущую программу.
retry: NOT_FOUND 404
transport routes: v2/workouts/sync × 3
```

Причинная цепочка в коде:

1. [WorkoutsService.start](../../src/services/workouts.ts) сохраняет active-запись
   до первого sync. При жёстком 404 start бросает ошибку, но запись остаётся.
2. end('abort') сначала устойчиво фиксирует pendingEnd. sync сначала пытается
   зарегистрировать выполнение/доставить события; при 404 до /abort дело не доходит.
3. unfinished учитывает active и pendingEnd. start, prepareLogout и
   [integration.ts](../../src/features/workouts/integration.ts) блокируют другой запуск.
4. [runner.ts](../../src/features/workouts/runner.ts), render: pendingEnd означает
   saving, start/stop скрыты; доступен только retry. При несовместимом API retry
   не может завершить операцию. select на «Сегодня» возвращает к прежней программе.
5. [bootstrap.ts](../../src/app/bootstrap.ts) повторяет refresh/sync при загрузке,
   навигации и возврате; признак несовместимости не отделён от временной ошибки сети.
   refreshActivity также может очистить общий error, не устранив ошибку завершения.

Принудительное удаление записи было бы опасным «исправлением»: synced=false не
доказывает, что сервер ничего не получил (ответ мог потеряться), events=[] не означает
отсутствие уже подтверждённого объёма, нулевой прогресс не доказывает отсутствие
серверной active-сессии.

## Цель и общий контракт исправления

Пользователь явно продолжает активную программу либо прекращает её с сохранением
фактического объёма. После подтверждённого abort запускается другая программа.
Несовместимый сервер обнаруживается до нового онлайн-старта; существующая работа
сохраняется и становится доступна для безопасной отправки после восстановления API.
Никакого ложного сообщения «отменено/сохранено».

HTTP-контракт остаётся [существующим](../API.md):

| Операция | Вход | Ответ |
| --- | --- | --- |
| GET /api/v2/workouts/catalog | Без тела | {programs,rulesVersion:"workout-v1",serverNow} |
| GET /api/v2/activity | Без тела | ActivityProgress |
| GET /api/v2/workouts/history?limit=1 | limit, cursor optional | {items,nextCursor,limit,serverNow} |
| POST /api/v2/workouts/sync | {workout:{id,programId,startedAt},events:[…]} | {accepted,duplicate,workout,progress} |
| POST /api/v2/workouts/:id/abort или finish | {endedAt,activeMs} | {workout,progress} |

- Auth: прежняя индивидуальная Bearer-сессия, профиль обязателен; без auth 401,
  без профиля 409 PROFILE_REQUIRED; Origin/JSON для POST сохраняются.
- Успех 200 с валидным JSON, private/no-store. У workout API нет fallback на v1.
- NOT_FOUND/API_NOT_FOUND на ожидаемом маршруте означает возможную несовместимость,
  WORKOUT_NOT_FOUND означает конкретное недоступное выполнение: не смешивать.
- NETWORK/TIMEOUT, 401, 409, 404 и неверный JSON обрабатываются раздельно.
- UUID выполнения/событий и pendingEnd сохраняются при retry/reload; сначала ack
  всех событий, затем неизменённое завершение. XP не начисляется повторно.
- Продолжение только явно и до 24 часов; поздняя доставка в существующем окне 7 дней.
  Просроченные за пределами доставки записи не объявлять успешно восстановленными.
- История сохраняет текущие limit/cursor и порядок; ActivityProgress сохраняет
  монотонную version и serverNow. Wire-форматы и версии правил не меняются.
- Локальные состояния доступности API и доставки результата — разные признаки.
  Успех обновления XP не должен стирать причину ошибки завершения.
- Камера не запускается автоматически после запроса, retry, отмены или reload.

Ожидаемое отображение:

| Состояние | Действия |
| --- | --- |
| Active, нет pendingEnd, срок не истёк | Продолжить / Завершить досрочно |
| Active, прошло 24 часа | Сохранить частичный итог; продолжение недоступно |
| Есть pendingEnd | «Завершение ожидает подтверждения» / Повторить сохранение; не предлагать возобновление уже прекращённого выполнения |
| Известно отсутствие workout API | Объяснить несовместимость приложения и сервера / Проверить снова; работа сохранена, бесконечных POST нет |
| Подтверждён aborted/completed | Показать фактический итог / Выбрать новую программу |

Блокировка второй программы до ack остаётся защитой данных. Исправление устраняет
неработающий путь восстановления и скрытую причину блокировки; не разрешает вторую
программу поверх неподтверждённой первой и не обещает серверную отмену без сервера.

3. Read-only checker не отправляет POST и не маскирует 404/неверный JSON/401/нет профиля.

4. Указан порядок для зависшей записи: восстановить совместимый API → отправить
   прежние UUID → подтвердить очередь → отправить прежний pendingEnd → новый запуск.
5. Если маршрутизатор и abort уже правильны, допустим результат без продуктовой
   правки server/*.js: checker/проверки/отчёт. Отсутствие публикации не объявлять
   исправленным развертыванием.

**Проверки:** только затронутые workouts-server/backend-deploy/readiness сценарии;
workout-contracts при затрагивании маршрутов/ответов. Полный набор и build/dry-run
оставить одной финальной контрольной точке общего исправленного SHA.

## Владельцы, зависимости и порядок интеграции

- Общие api.ts, validate.ts, workouts.ts и validate-workouts.ts в shared/contracts,
  а также docs/API.md — **единственный владелец Backend**, если вообще понадобится
  менять HTTP-контракт. В текущем пакете новые endpoint/поля не запланированы:
  не делать пустые правки этих файлов. Любое обнаруженное необходимое расширение
  сначала оформить конкретным diff; документация/типы/парсеры/проверки в одном PR.
- Frontend владеет локальными состояниями, журналом и UI. Оба исполнителя не меняют
  версии независимо: окончательную версию/APK versionCode фиксирует Тимлид при
  сборке общего исправленного кандидата.
- Backend сначала возвращает факт совместимости/причину 404. Frontend может
  параллельно исправлять клиент на существующем контракте и тестовой несовместимости;
  реализация не ждёт публикации основного сервера.
- Тимлид согласует результаты обоих PR, сохраняет ссылки/SHA в HANDOFF, фиксирует
  общий SHA и один финальный прогон/сборку. Полные проверки не дублируются по чатам.
- До разрешённого выпуска на телефоне не очищать данные, не выходить из профиля
  ради обхода и не удалять приложение. Серверная отмена не обещается до восстановления API.
- Main, remote-миграции, публикация и ручные UPDATE/DELETE на основной D1 не разрешены
  этой постановкой. При подтверждённом старом сервере подготовить конкретный
  совместимый кандидат и порядок выпуска для отдельной команды владельца.
- Независимую проверку другим разработчиком не назначать. Сохраняются прежние
  модель/WASM/алгоритмы, XP, UUID-before-send, ack-before-end и минутные инварианты.

Передача каждого исполнителя: PR/base/head SHA, изменённые файлы, причина и
